# 学者与译稿审校对 RefRain 的意见书

> 评审对象：RefRain 本地写作工作台
> 评审依据：`SPEC.md` v0.1.2 · `设计计划.md`（第五、六、七、九节）
> 评审者身份：角色 A —— 人文社科学者（历史学／社会理论）；角色 B —— 出版社文字编辑／译稿审校
> 日期：2026-07-26

# 上篇 · 角色 A：人文社科学者

## 1. 我是谁

我做近代东亚思想史，兼做社会理论。手上一部专著、每年两三篇期刊论文。材料是中日英三语的一手档案与二手文献，一章正文常带一百二十个脚注。工具栈：Zotero + LaTeX/Overleaf 写论文，Scrivener 起草长章，Obsidian 存卡片，Word + EndNote 应付要求修订稿的期刊，ChatGPT/Claude 只敢用来做文献综述的粗筛。我的职业焦虑只有三条：引文是否逐字准确、学术诚信是否可证、以及**我能不能证明这句话是我写的**。

## 2. 我的三个高频场景

**场景一 · 带引文的段落重写。** 一段两千字的论述，中间嵌了三条引文：一条日文原文（《明六雜誌》影印本录文）、一条英译（Bellah 的译法）、一条我自己的中译。我想让 AI 把这段的论证节奏收紧——但那三条引文里的每一个字符，包括日文旧字体、破折号、省略号的形态，**一个都不许动**。

**场景二 · 跨章节术语与译名统一。** 全书把 `Gemeinschaft` 一律作「共同体」而非「共同社会」，「国体」保持原词不译。写到第七章我改了主意，要回头统一。这意味着一次要在六个文档里改三十几处，且每一处都得看上下文判断是不是同一个词义。

**场景三 · 投稿前的贡献归属自查。** 期刊现在要求 AI 使用声明。我必须回答：哪些句子是我从零写的、哪些是 AI 建议我原样接受的、哪些是 AI 建议我改写后采纳的。今天我靠的是记忆和 git commit message，两者都不可靠。

## 3. 眼前一亮的地方

**（1）「Agent 绝不直接写正文」被写成了不变量，而不是承诺。** `SPEC.md` §3.1 与 §9.1 把「Only a Text Action mutates the manuscript」列为白盒不变量并要求测试覆盖，`AGENTS.md` 把违反它定义为 bug 而非风格偏好。这比任何一家厂商在博客里写的「我们尊重作者」都可信一个数量级。我用 Word 的 Copilot 时最恐惧的就是它悄悄替我「优化」了一句引文而修订标记没跟上。

**（2）Verdict Ledger 的 `reason` 字段被认真对待。** `SPEC.md` §7.2 明文规定「presence and absence must remain distinguishable — never paper over the difference with an empty string」。这是一句很小的规定，但它意味着设计者知道「我没写理由」和「我写了理由但理由是空的」在学术审计里是两件事。这个洁癖我认。

**（3）Result Artifact 的解析器安全边界。** §7.1 明确禁用 DTD、外部实体、网络访问，拒绝未知元素、重复 replacement、非法 UTF-8。做多语种材料的人吃过 XML 实体和 BOM 的亏。加上 `设计计划.md` 7.5 节要求「完成时重新核验前两段没有被修改」——即 Agent 不能篡改「修改前文字」区段——这是全套设计里最接近「引文保护」的一处机制。

## 4. 会让我立刻放弃的地方

**（1）没有引文保护机制。一个都没有。** 这是致命的。我通读了 `SPEC.md` §2 全部域语言表和 `设计计划.md` 第五节，没有任何一个概念叫 Quotation、Citation、Immutable Span 或 Protected Range。Edit Scope（§2.2）的定义是「a manuscript slot a run may replace」——**它保护的是范围之外，不保护范围之内**。我把一个含三条引文的段落设为 Edit Scope，Agent 就有权把那三条引文连同周围的论述一起替换掉。设计里唯一的防线是我逐 Review Slice 肉眼比对。

这还不是最糟的。最糟的是 `SPEC.md` §1.3 与 `设计计划.md` 4.2 节把「学术引文……的完整领域模块」明确列为**不做**。我理解首发范围要收窄，但请注意区别：我要的不是 Zotero 替代品，不是参考文献格式化，不是文献库。我要的是一个**在 Edit Scope 内部标记「这几个字符是不可变引文」的原语**，并在 Review Engine 校验 Proposal 时，只要 replacement 中该区间的字节不逐字相等就直接判校验失败——和你们对「前两段哈希」做的事一模一样。这是 core 里几十行的活，不是一个领域模块。

**（2）Review Slice 是「确定性 diff 片段」，但没有说粒度。** §2.2 只说 deterministic diff fragment。对我来说，一条 diff 如果是段落级的，等于没有：一个八百字的段落里 Agent 把日文引文的「ゝ」改成了「々」，段落级 diff 只会告诉我「这段被替换了」。我要的是字符级、且对 CJK 与全角标点敏感的高亮，最好能对「仅标点/仅字形变化」单独打标。`SPEC.md` §10 的性能项里提到了 CJK 输入与 IME，却没有一条提到 diff 算法在 CJK 上的正确性。这是全套文档里我最不安的沉默。

**（3）Verdict Ledger 无法回答「这句话是谁写的」。** §1.2 声称 audit 能力是「show which sentence a human wrote, which an agent proposed, and which an agent proposed and a human revised」。但看数据模型：`Verdict` 只有 `proposalId` / `sliceId` / `kind` / `finalText` / `baseline`（§7.2）。归属信息挂在**决定**上，不挂在**文字**上。Decision Batch 落地后产生一个 Text Action 和新 Text Head（§7.4），此后我在那段文字上继续手写三轮，谁还知道第三句的前半截来自 Proposal p-17？要回答「这句是谁写的」，必须从 Text Head 反向追溯 Text Change 谱系再关联 Decision Batch——`设计计划.md` 6.2 节确实保存了「稳定文档／范围谱系」，但没有任何一处承诺提供**从当前字符位置到归属来源的正向查询**。而 §12 的 Q4「Verdict Ledger 的检索接口是否在 v1 发布」还挂着 Open。**Moat 写在 §1.2，接口却是开放问题**——那我在投稿前那份 AI 使用声明就写不出来。

**（4）Source Backup 是安慰剂，不是防线。** §2.1 与 `设计计划.md` 6.1 节说得很清楚：Source Backup 只在「从既有文件建立项目时」保留一次不可变原件。之后我写第三稿、第八稿、终稿，它还停在第一天。它能证明的只是「我最初拿到的文件长这样」，保护不了任何一条我在写作过程中新引入的引文。真正在保护正文的是 Text Head 链 + Revision，而那是活的、可被 Decision Batch 推进的。把 Source Backup 当作引文安全的答案是误读。

## 5. 它可以如何重塑我的工作习惯

**（1）把「AI 使用声明」从事后回忆变成事前记账。** 如果 Verdict Ledger 的检索接口进 v1，并且能按文档、按章节导出一张「本章 N 句为 accept、M 句为 accept-modified，各附 reason」的表，我就可以把它直接贴进投稿材料。今天没有任何一个工具能给我这个，这会是我换工具的唯一充分理由——比编辑器好不好用重要得多。

**（2）把「与 AI 讨论」从聊天窗搬回稿面。** `设计计划.md` 8.1 节的群 Agent 竞争 + 8.2 节 Discussion Round，恰好对应我现在的坏习惯：同一段话开三个 ChatGPT 标签页各问一遍，然后手动拼。竞争 Proposal 落在同一基线 Revision 上、可并排比较、可部分采纳、拒绝也留审计——这确实比标签页文明。前提是引文安全先解决，否则我一次都不敢发。

## 6. 如果只能改一件事

**在 core 里加一个 Protected Span 原语，并让 Review Engine 用哈希强制它。** 具体：允许作者在正文中标记不可变区间（引文、原文录文、法条、他人译文），该标记随 Text Change 谱系迁移；任何 Proposal 的 replacement，若其覆盖的 Protected Span 内容与基线 Revision 不逐字节相等，则**在 Proposal 冻结阶段就校验失败**，连 Review Slice 都不生成——和 §7.5 对「前两段哈希」的处理完全同构，复用现成机制。做不到这一条，RefRain 对学术写作就是一个漂亮但不可用的工具；做到了，它是我这十年见过唯一敢用的。

# 下篇 · 角色 B：出版社文字编辑 / 译稿审校

## 1. 我是谁

某社外版书编辑室，做引进版学术书与非虚构的译稿审校，一年过六到八部稿子。我的工作不是「读译文顺不顺」，而是**对着原文逐句核校**：漏译、误译、术语漂移、专名不统一、注释错位。工具是 Trados 和 memoQ（做双语对照与术语库），交译者时用 Word 修订模式加批注，往返三到五轮。我的焦虑是术语一致性、原文译文的对照视图、以及修改意见的可追溯——三样缺一样，这稿子就要返工。

## 2. 我的三个高频场景

**场景一 · 双栏逐句核校。** 左栏英文原文，右栏中译，句对齐。我从头往下走，遇到问题就在右栏挂批注：「此处 institution 前文作『制度』，此处作『机构』，请统一」。一天走两万字。

**场景二 · 术语表驱动的全稿扫描。** 交稿前建一份术语表（原文词 → 认可译法 → 禁用译法），跑一遍全稿，把不符项列成清单发给译者。学术书这份表常有两三百条，专名占一半。

**场景三 · 三轮往返的意见追溯。** 我提的意见，译者可能接受、可能反驳、可能改成第三种说法。到第三轮我需要回答主编：这个词为什么最后定成这样？我得能翻出第一轮我写的理由和译者的答复。今天靠 Word 批注串加邮件，经常断线。

## 3. 眼前一亮的地方

**（1）Verdict 的 `reason` 就是我的批注，而且它落盘、可检索、可回传。** `SPEC.md` §7.2 的 `reason` 加上 §7.3 的回传格式，本质上是把我在 Word 里写的批注变成了结构化数据，并且能作为下一轮 prompt 的一部分发回去。Word 批注的宿命是导出成一份没人再打开的 Excel；这里它是**下一轮输入**。这一点比我见过的任何 CAT 工具都往前一步。

**（2）「修改后合并不改写原 Proposal」。** `设计计划.md` 7.7 节：「修改后合并保存用户最终文字，但不改写 Agent 原 Proposal，因此可以审计『Agent 建议了什么』和『用户最终写了什么』」。这正是我三轮往返里最想要的那条线索——译者交了什么、我改成了什么、两者并存。Word 修订模式接受后就把痕迹吃掉了。

**（3）冲突不由系统偷偷决定胜者。** §7.4 第 4 条、`设计计划.md` 7.8 节第 4 条都写明：映射后 Text Change 必须互不相交，冲突则整批不提交，「系统不以隐藏顺序决定胜者」。做过多人合稿的都被 Word 的合并功能坑过。这条规矩我举双手赞成。

## 4. 会让我立刻放弃的地方

**（1）没有对照视图。一个字都没提。** 我把 `SPEC.md` 全文和 `设计计划.md` 7.6 节读完，视图只有两种：正文幽灵对比（把 Proposal 投影到正文位置）和独立检阅窗口（显示修改前文字、替换文字、Agent 意见）。这两种视图的三个栏位是「基线正文 / Agent 替换 / 当前正文」——**没有一栏能放原文**。对我来说，「修改前文字」是译文的上一版，不是原文。原文在另一个语种、另一个文件里，而这个数据模型压根不知道它存在。一个连双语对照都没有的工具，在译稿审校这个场景里不是「功能少」，是**根本没进门**。Context Scope（§2.2）理论上可以把原文塞进去让 Agent 读，但那是喂给模型的，不是给我看的——我要的是我自己的眼睛能逐句对齐地看。

**（2）术语一致性无处安放。** 域语言表里没有 Glossary、Term Base、Termbase 或任何等价物；`设计计划.md` 4.2 节把「资料管理」也划进不做。于是我的两百条术语表只有两个去处：塞进 prompt（每个 Run 都塞一遍，且没有任何机制保证 Agent 遵守），或者写进「项目规则」（5.1 节 Project 定义里提到了「项目规则」，但全文没有第二处解释它是什么、如何生效、是否参与校验）。更关键的是：**术语一致性是一个全稿属性，而 Edit Scope 是局部的**。RefRain 的整个协作模型是「选一段、发一次、裁决一次」，它在结构上无法表达「这个词在全书六个文档三十七处必须一致」这类约束。

**（3）Edit Scope「一个 Run 只能绑定一个连续修改范围」对逐句校译是致命的。** `设计计划.md` 5.3 节写死了：「一个 Run 只能绑定一个连续 Edit Scope；多个不连续位置必须拆成多个 Run」。而 `SPEC.md` §2.2 却写「One Review Task may carry **several disjoint** Edit Scopes」——先说一句：**这两份文档在这一点上不一致，请先裁决。** 但无论哪种，落到 Run 粒度都是一个 Run 一个连续范围。

对逐句核校意味着什么？我一天走两万字，一章里典型是四十处零散问题：这里漏了个从句、那里专名错了、隔两页术语漂了。这在 RefRain 里是**四十个 Run**。四十次模型调用、四十个 Task Workspace 目录、四十份 Result Artifact、四十个 Review Window。哪怕它们能进同一个 Decision Batch，我也得点四十遍。而我在 memoQ 里做同样的事是四十条批注、一次发送。这不是效率差一点，这是量级错配——这个模型是为「重写一大段」设计的，不是为「密集点状修订」设计的。

**（4）没有段落/句对齐的稳定身份，往返就断线。** §2.2 说 comment 的 `target` 必须是「a stable boundary ID the system supplied」，`设计计划.md` 6.2 节也保存「稳定文档／范围谱系」。这很好——但边界是**段落／块级**的。译文一次修订常常合并两句、拆开一句、调换语序，段落 ID 稳定不代表句子对得上。做了三轮之后，我第一轮挂在第 12 句的批注还能不能定位到现在的第 12 句？文档没有回答。而这正是 CAT 工具用 segment ID + TM 解决了二十年的问题。

## 5. 它可以如何重塑我的工作习惯

**（1）把「意见—答复—定案」的链条从邮件里救出来。** 如果 Review Decision Event（`设计计划.md` 5.2 节）加上 Thread（可定位到正文选区、有 `open/resolved` 状态）真的做出来，我三轮往返的全部理由就都在稿子里、可检索、带状态。主编问「这个词为什么定成这样」，我点开那一处就能答。这一条足以让我把 Word 批注扔掉——前提是对照视图先存在。

**（2）把术语扫描从人肉变成可裁决的批量提案。** 群 Agent 竞争（8.1 节）+ 一次 Decision Batch 提交多处不相交 Text Change（7.8 节第 6 条），理论上支持「一次扫全章、生成三十七处术语修正、我逐条裁决、一次落盘」。这正是我最想要的形态。但它撞上第 4.3 条：一个 Run 一个连续范围，三十七处就是三十七个 Run。**能力在数据层是通的（Decision Batch 支持跨章节多处不相交 Text Change），卡死在派发层。** 这是一个设计缺口，不是一个实现难题。

## 6. 如果只能改一件事

**允许一个 Run 绑定多个不连续 Edit Scope，并让 Result Artifact 的 `<replacement scope="...">` 支持多槽位。** `SPEC.md` §7.1 的 schema **已经有 `scope` 属性了**，§2.2 也已经写了「several disjoint Edit Scopes」——真正拦路的只有 `设计计划.md` 5.3 节那句「一个 Run 只能绑定一个连续 Edit Scope」。请把两份文档对齐到宽的那一侧，并把「一次 Run、多处点状修订、一个 Decision Batch 落盘」列为验收路径。这一改，密集点状修订从四十个 Run 变成一个，逐句校译才从「不可能」变成「可能」。对照视图和术语库可以排到 v2；这一条排到 v2，v1 就没有译稿审校用户。

---

> **两个角色共同的一句话：** RefRain 在「人类裁决不可绕过」这件事上做得比我见过的任何工具都硬，这是它的资产。但它当前的域语言只认识「一份正文」——不认识引文的不可变性，也不认识原文与译文的并置。这两样都不是功能，是**数据模型层面的缺席**。补在 v1 是几十行；补在 v3 是重写。
