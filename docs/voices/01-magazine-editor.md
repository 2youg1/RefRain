# 一位杂志社资深编辑对 RefRain 的意见书

> 评审对象：RefRain 本地写作工作台
> 评审依据：`SPEC.md` v0.1.2、`设计计划.md`
> 评审者：某文学／非虚构月刊资深文字编辑，从业第 16 年
> 日期：2026-07-26

---

## 一、我是谁

某月刊资深文字编辑，第 16 年。手上常年压着 8 到 12 篇稿：非虚构特稿 8000–20000 字，社科评论 5000–12000 字，中篇小说 3 万字上下。一篇稿从约到发，平均 4 轮往返、6 周。我一天里最长的时间不是写作，是**在别人的句子上做决定**——改还是不改，以及为什么。

---

## 二、我的三个高频场景

### 2.1 逐句退改：一篇 14000 字特稿的第二轮

我打开 Google Docs 建议模式，从头走到尾，平均留下 180 条建议、40 条批注。

卡在哪里：**「移动」这个动作在建议模式里根本不存在。** 我要把第三段的两个句子换个顺序、同时保留作者原来的用词，Docs 只能记成"删掉这两句"加"在另一处插入这两句"——四段红色。作者打开文档，看到的是我把他的段落删了，不是我把顺序调了。他为此写了三百字邮件问我为什么删。其次，我的理由写在批注气泡里，作者一点 Resolve，理由连同上下文一起蒸发。三轮之后，没有任何地方能回答"这一句当初为什么这么定"。

### 2.2 三稿清样：统一体例而不碰引文

定稿前我做一次全稿体例扫。Word 查找替换：正文里的"其后"统一成"之后"，西文引号统一成中文引号，年份的"零"统一成"〇"。

卡在哪里：**替换不认语境。** 引文里的"其后"必须原样保留——那是别人的原文，改了是硬伤。所以我不敢用"全部替换"，只能按 187 次"查找下一处"，每次自己判断。做完发现有一处引文被误改，想撤销那一次替换——Word 只能一路 Ctrl+Z 回去，把后面两小时的改动一起赔掉。我通常选择不撤，手工改回来，并祈祷没有第二处。

### 2.3 第四轮：回答"你上次为什么删掉那段"

作者三周后回信：第二轮你把那段家族史删了，我想加回来。

卡在哪里：**我的裁决没有存档。** 理由散在批注里（已 Resolve）、邮件里（三封）、微信里（一段语音）。我要花二十分钟考古，还未必找得到。更糟的是，我对同一位作者的判断有稳定倾向——我一贯砍他的排比、一贯保留他的方言词——但这套倾向只活在我脑子里，交不了班，也喂不进任何工具。

## 三、这个产品让我眼前一亮的地方

**1. Selective Undo 直接命中 2.2。**
"在 10,000 项不相交后续行动之后撤销第一项，不回放中间历史"（设计计划 §6.5、SPEC §11 M1 验收）——这正是我在 Word 里做不到、且每一稿都要吃一次亏的事。撤掉第三轮那次误替换，保留后面两小时的全部改动；而且冲突时它不自作主张，而是把"A1 修改前／A1 修改后／当前文字"三样摆出来等我裁决（§6.5）。没有一款文字工具给过我这个。

**2. Verdict 的 `reason` 落盘，直接命中 2.3。**
把"接受／拒绝／修改后合并 + 为什么"存成一等公民数据（SPEC §1.2、§7.2），而不是一个用完即焚的 UI 事件——这是这个产品唯一真正新的东西。SPEC §7.2 里那句"present 和 absent 必须可区分，绝不用空字符串糊过去"让我确认设计者知道自己在做什么：一个能被空值污染的账本，三个月后就是垃圾。

**3. 修改后合并不改写原 Proposal，我们社的合规问题因此有了物证。**
§7.7："修改后合并保存用户最终文字，但不改写 Agent 原 Proposal，因此可以审计 'Agent 建议了什么' 和 '用户最终写了什么'。"发稿前无法证明哪一句是人写的，这是我们现在最迫切的问题。这条规则一落地，署名和责任就有了可查的凭据。

顺带记一功：SPEC §3.4 推翻了设计计划 §3.4 的"压缩即永久冻结"，理由是"那等于一天办好几场葬礼"。谢谢。我一晚上处理一章，中途死掉一个协作者、还要我把上下文重新交代一遍，我第二天就换回 Docs。

## 四、这个产品会让我立刻放弃的地方

这一节我说得不客气，因为每一条都是我一天里会撞上十次的地方。

### 4.1 「一个 Run 只能绑定一个连续 Edit Scope」——这条规则会杀死这个产品

设计计划 §5.3 白纸黑字：「一个 Run 只能绑定一个连续 Edit Scope；多个不连续位置必须拆成多个 Run。」

我的第二轮退改是 180 处，散在 14000 字里。按这条规则，那是 **180 个 Run**。180 次派发、180 个 Task Workspace、180 份 Result Artifact、180 个检阅窗口。就算合成一个 Decision Batch，前面那 180 次的建立成本也已经把我压死了。

而且这条规则和 SPEC §2.2 自相矛盾——SPEC 写的是「One Review Task may carry **several disjoint** Edit Scopes」。两份文件在同一件事上说反了，而这件事决定产品能不能用。**如果最终按设计计划的写法落地，我第一天就退回 Docs。** 我要的是一次请求覆盖多个不连续位置（全稿的「其后」、三处需要压缩的转场），一次拿回来，一屏裁完。

### 4.2 没有「移动」这个原语，场景 2.1 原样复现

我翻遍了两份文档的领域语言。Text Change 的类型只有「文档内文字变化」和「文档清单的新增／移除／重命名／重排」（§6.2）。**段落级、句子级的"移动"不是一等操作。**

于是我把第三段两句换序、保留原用词这件事，在 Review Slice 里仍然会看到一处删除加一处插入。作者仍然会以为我删了他的句子。**这是我离开 Google Docs 的头号原因，而这个产品把它原样继承了。** 讽刺的是这里本该是它的主场：既然 Text Change 已经有稳定 ID 和范围谱系，认出"同一段文字换了位置"比 Docs 容易得多。没做，是漏了，不是难。

### 4.3 「Agent 工作时正文对人类只读」——如果这条成立，我不用

SPEC §12 Q2 还开着，但倾向写得很清楚：「the file is read-only to the human while an agent works on it」。

我一晚上要开五六个请求，让它们跑着，同时我自己在别的章节改。**要是派一个 Run 就锁我一次正文，这个工具就是我的甲方而不是我的助手。** 现有设计其实已经解决了这个问题——Proposal 绑定基线 Revision，drifted 会被标记（SPEC §3.5），三方比较兜底（§8.3），检阅窗口"不抢焦点"（§7.6）。既然映射机制都在，就不该再加锁。**Q2 如果答成只读，前面所有工程都白做了。**

### 4.4 检阅一次只能投影一个 Proposal，等于逼我在两个软件之间选

§7.6：「正文同时只投影一个 Proposal，其他竞争 Proposal 留在检阅列表中按需切换。」

我把同一段广播给三个 Agent（§8.1 明确支持竞争），拿回三个版本。我最常做的事是**手工综合**——A 的开头、C 的收尾、我自己改动词。设计计划自己在 §8.1 里把"手工综合"列为受支持的用户动作，然后 §7.6 又只给我一个投影位，让我靠切换去比。三个版本靠记忆比对，我不如把三段粘进 Word 分栏。**要么给我并排三栏，要么别声称支持竞争 Proposal。**

### 4.5 找不到裁决的入口，账本就只是硬盘上的日志

SPEC §12 Q4 开着：「Verdict Ledger 的检索接口是否随 v1 交付？」

我直说：**没有检索接口，这个账本对我等于不存在。** §1.2 承诺的三件事里，「Reply」和「Audit」都能靠写入侧成立，但「Taste」不行——口味画像必须能被翻出来看。场景 2.3 里我要的是「把我对这位作者所有 kind=reject 的裁决按理由列出来」。这一句查询就是这个产品对我的全部价值。**Q4 答"不"，剩下的功能我在 Docs 加 Word 里都有替代品。**

### 4.6 冲突时整批拒绝提交，深夜会要我的命

§7.8 第 4 条、SPEC §7.4 第 4 条：映射后的 Text Change 必须两两不相交，「两个决定重叠……整批不能提交」。

原则我完全同意——系统不该靠隐藏顺序挑赢家。但请想象凌晨一点，我裁完 60 个切片点提交，因为其中 2 个重叠，整批弹回。**如果这时候界面只给我一句"批次冲突"，我会当场砸键盘。** 我要的是：把那 2 处高亮出来、其余 58 处让我先落盘、冲突范围里直接给我一个可编辑框写最终文字。§7.8 提到了"用户必须在冲突联合范围内给出一份最终 replacement"——这句话必须是一个**就地可编辑的控件**，不是一条错误提示。

## 五、它可以如何重塑我的工作习惯

**1. 我会开始写下理由，因为理由第一次有了去处。**
我现在不写理由，不是懒，是因为写了也会被 Resolve 掉。如果 `reason` 落盘、可检索、可回传（§7.2、§7.3），那么每写一条理由都是在给未来的自己和 Agent 攒资产。第四轮我不再考古二十分钟，我查账本。**这一条能把我每篇稿的沟通成本砍掉三分之一。**

**2. 我会从「亲手改」转成「先派、后裁」。**
现在体例统一是 187 次人肉「查找下一处」。如果能一次派出去、拿回一批 Review Slice、我用键盘逐条 accept／reject，这活从两小时变成二十分钟。前提是 4.1 必须修——**多 Edit Scope 是这条习惯改变的唯一开关**。

**3. 我会开始交接我的口味。**
我们组带新人靠口传心授，三年才带出一个。如果账本能导出成"这位编辑对这位作者的 300 条裁决及理由"，那是我从业 16 年第一次能把判断力交出去的形式。这比任何"AI 写作助手"都值钱——它不生成文字，它保存判断。

---

## 六、如果只能改一件事

**把「一个 Run 只能绑定一个连续 Edit Scope」（设计计划 §5.3）改成 SPEC §2.2 已经写下的「一个 Review Task 携带若干互不相交的 Edit Scope」，并按此贯通派发清单、Result Artifact 的多 `<replacement scope>`、检阅列表和 Decision Batch。**

理由：SPEC §7.1 的 Result Artifact 格式**本来就支持**多个 `scope`，Decision Batch 的组合语义（§7.4）本来就按多份 replacement 设计，交换律和三方映射都已经就位。也就是说，整条管线已经为多范围建好了，只有 Run 的绑定规则卡在单范围上。这不是新增功能，是**拆掉一颗装错的螺丝**。

拆掉它，我一次请求覆盖全稿 180 处，一屏裁完，一个批次落盘，账本上留下 180 条带理由的裁决。不拆，我要建 180 个 Run——而我不会建到第 5 个就把这个软件关掉了。

*—— 一个用了十六年红笔、三年建议模式、被 Notion AI 和 Sudowrite 各骗过一次的人。*
