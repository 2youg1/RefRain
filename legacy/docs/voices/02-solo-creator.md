# RefRain 用户意见书 · 02 · 重度 AI 协作的一人公司创作者

> 评审对象：RefRain（本地 AI 写作工作台）
> 评审依据：`SPEC.md` v0.1.2、`设计计划.md`（1360 行）
> 立场：付费用户视角，按分钟精算时间成本

## 一、我是谁

一人公司，内容是唯一产品线：每周一封 6000 字长文 newsletter、每周两期播客脚本、手上一本出版合同的书稿。日均产出约 8000 字成稿。每天与 Agent 并行协作 6 小时以上，Claude Code 与 Codex 常驻，自己写 skill、配 MCP、开三到四路 agent 竞跑。付费在跑：Claude Max、ChatGPT Pro、Cursor、Sudowrite、Lex、Notion AI、Ulysses、Scrivener。核心焦虑三条：产能、上下文管理、以及「AI 写的东西怎么才算我的」。

## 二、我的三个高频场景

### 场景 A：早上 7:00-9:00，newsletter 初稿的「三路竞跑」

我把大纲切成 12 个 section，开三个 agent：一个走论证密度，一个走叙事节奏，一个专门做反驳视角。三路同时对同一批 section 出稿，我在中间做拼接。

目前怎么做：三个终端窗口 + 一个 Obsidian 主文档，手工复制粘贴。
卡在哪里：**没有任何工具帮我记住我为什么选了 A 而不是 B**。第三周我会发现自己在对第 47 个段落重复同一句反馈——「这里别用设问句结尾」。我已经说过 40 次了，每一次都随着终端 scrollback 一起消失。这是 RefRain 的 Verdict Ledger 直接命中的痛点，我承认。

### 场景 B：下午，书稿章节的「逐句校订」

出版社编辑退回的一章，两万字，标了 60 处。我要判断哪些接受、哪些据理力争。

目前怎么做：Word 修订模式 + Claude 做二次意见。
卡在哪里：修订模式的接受/拒绝是**一次性 UI 事件**，点完理由蒸发。三个月后二校，同一个争议点重来一遍，我完全不记得当初为什么坚持。SPEC §1.2 说「Click accept, and the reasoning evaporates」——这句话是对的，写这句话的人真的做过这件事。

### 场景 C：晚上，播客脚本的「口语化重写」

书面稿转口播稿，整篇每一段都要动。一集脚本约 5000 字、40 个段落，段段有改动。

目前怎么做：Sudowrite 整段重写，我扫一遍，八成直接留下。
卡在哪里：这是**低价值、高密度**的裁决场景。40 个段落，我真正会推翻的不超过 5 个。剩下 35 个我的决策是「行，过」。任何要求我为这 35 个都点一次、并且最好写个理由的系统，都是在向我收一笔我不愿付的税。这一节请产品团队记住，第四节我会回来算账。

## 三、让我眼前一亮的地方

**1. Verdict Ledger 是我买过的所有工具都没做对的那一件事。**

`reason` 字段被写进 SPEC §7.2，并且明确规定「present and absent must remain distinguishable — never paper over the difference with an empty string」。这行字比整个产品页的营销文案都有说服力。我付费给 Sudowrite 两年，它至今不知道我讨厌设问句结尾。RefRain 把 Verdict 序列化回 prompt（§7.3 那个按 `n` 排序、前缀字节稳定所以能命中缓存的设计），意味着我第 41 次说「别用设问句」时，agent 已经带着前 40 次进场了。这不是 feature，这是复利。

**2. Decision Batch 的冲突拒绝规则，救过我的命。**

SPEC §7.4 第 4 条：映射后的 Text Change 必须两两不相交，冲突则整批不提交，「the system never picks a winner by hidden ordering」。我在 Cursor 里被隐藏顺序坑过——两个 agent 改同一段，后写的静默覆盖先写的，我三天后才发现丢了一整段论证。宁可让我手动拆批次，也别替我猜。这条我毫无保留支持。

**3. 「不替用户算钱」是一个我等了很久的产品姿态。**

SPEC §3.3：token 只有 actual / estimated / unknown 三态，unknown 不写成 0。Claude Code 显示的美元数字是本地估算，官方文档自己都说不能用于对账；我见过太多工具把估算值印成账单模样，然后我按它做预算决策，月底被真账单打脸。`Capability<T>` 把 unknown 做成一等值，这是工程诚实。

## 四、会让我立刻放弃的地方

这一节是重点。我按「一天损失多少分钟」来排。

**1. 「逐句点击」在场景 C 是灾难，而产品没有为场景 C 留出口。**

先算账。播客脚本 40 个段落全改，我实际推翻 5 个。如果每个 Review Slice 需要一次定位 + 一次阅读 + 一次点击，乐观估计 8 秒。35 个「行，过」× 8 秒 = 4.7 分钟。这还只是一集。我一周两集脚本、一封 newsletter、书稿若干，一天真实要处理的 Proposal 在 150-250 个之间。按 250 个算，纯裁决动作 33 分钟——**每天 33 分钟，一年 200 小时**，我用这些时间可以再写一本书。

我不是要 YOLO 模式。我完全接受「Agent 不能写正文」这条底线，甚至认为这是产品的立身之本。我要的是**人类批量裁决**：给我「全选接受」「本 Proposal 全部接受」「接受除标记外的全部」。SPEC §7.4 已经有 Decision Batch 这个原子容器了——一个 Decision Batch 里放 35 个 accept，仍然是一次人类点击、一次 Text Action、一次 Text Head。**这不违反任何不变量**，§9.1 那句「No automatic merge path exists」也完好无损，因为合并路径依然由人类那一次点击驱动。

但我在 SPEC 里读不到这个入口。§3.1 第 4 条只写了「merge as-is」和「merge revised」两条路径，§7.7 只写了「接受整个 Proposal」和「按 Review Slice 暂存接受或拒绝」。跨 Proposal 的批量裁决语义是缺失的。如果它不存在，我第一天就会退出。如果它存在但没写进 SPEC，那么按你们自己的规矩（「Do not invent decisions this document omits」），实现者不会做它。**这是一个规格空洞，不是一个交互细节。**

**2. Runtime Binding 永久冻结——SPEC 和设计计划在这里互相矛盾，而我站 SPEC。**

`设计计划.md` §3.4 写死：到阈值或压缩触发即 `frozen`，「提高阈值、修改设置、恢复进程或重新连接 Harness 都不能让原 Agent 回到 active」。

SPEC §3.4 直接推翻它：compaction 标记 lineage-unverifiable，是否换 agent 由用户决定，并且给了理由——「it stages a funeral several times a day and excludes most harnesses from the compatibility list」。

**写这句话的人替我说了话。** 我一个长稿 session 一天被 Claude Code 压缩三到五次。永久冻结意味着我一天要给同一个「编辑」办三到五次葬礼，每次都要重新派生、重新交代口味、重新授权 Automation Grant（§10 明写「派生 Agent 不自动继承父 Agent 的 Automation Grant」）。这不是严谨，这是把工具的形而上学洁癖转嫁成我的操作成本。

但这两份文件目前都在仓库里活着，AGENTS.md 说 SPEC 是权威，`agent-native-writing-design/AGENTS.md` 又说设计计划是单一入口。**作为用户我需要一个明确答复：冻结规则到底是哪一版？** 如果最终落地的是设计计划那版，我不会安装。

**3. Verdict 的 `reason` 是资产，也是税——而产品没说清它是不是可选。**

`reason?: string` 在类型上是可选的，好。但整个产品叙事都建立在「reason 是 ledger 最有价值的字段」上。我担心的是 UI 会用一个空输入框把我钉在原地。请明确：**空 reason 必须是零摩擦的一等公民路径，不弹窗、不提示、不高亮成待办。** 我一天 250 次裁决，其中值得写理由的大概 15 次。如果每次都要按 Esc 关掉一个提示，一天 250 次 × 1 秒 = 4 分钟，我不接受。

**4. 「一次一个 Proposal 投影」和多 Agent 竞跑是打架的。**

§7.6 结尾：「正文同时只投影一个 Proposal，其他竞争 Proposal 留在检阅列表中按需切换」。可我的场景 A 就是三路竞跑——我要的是**同一段的三个版本并排看**，不是切来切去凭记忆比较。切换成本每次 2-3 秒，而比较是我这个工作流的全部意义所在。多 Agent 广播（§8.1）在派发侧做得很完整，在裁决侧却退化成串行浏览。这条不改，多 Agent 对我就只是「多花三倍 token 换一个更慢的选择过程」。

**5. 缺一条从 Agent 侧发起的「整章体检」入口。**

§3.2 规定送审必须由用户选择完整段落、写 prompt、选 agent、看清单、点发送。这条防自动化的初衷我理解。但它把「我要 agent 通读全章、自己找出 20 个问题点」这件事变得很贵——我得先知道问题在哪，才能选中范围。而我雇 agent 就是因为我不知道问题在哪。

出路其实在你们自己的设计里：comment-only 结果（§7.6）不生成 Proposal，只进意见检阅。所以「整章 Context Scope + 零 Edit Scope + 只要意见」应该是完全合法的一次送审。**请把它变成一个一等的、有名字的动作**，而不是让我自己拼出来。

## 五、它可以如何重塑我的工作习惯

**1. 我会开始「养口味」，而不是「养 prompt」。**

现在我维护一份 2000 字的 style prompt，手写、手更新、每换一个模型重贴一遍。有了 Verdict Ledger，口味不再是我写出来的声明，而是我裁决出来的证据。这会改变我的日程：每周留 30 分钟读自己的 ledger，比每周花 3 小时调 prompt 划算得多。前提是 Q4（「Verdict Ledger 的检索接口是否进 v1」）答案为「是」——它现在还是 Open，而这恰恰是整个产品最值钱的部分。**没有检索的 ledger 是一口写入井。**

**2. 我会敢在书稿上用 AI 了。**

出版合同里有署名和原创性条款。SPEC §1.2 的 Audit 那条——成稿能指出哪句是人写的、哪句是 agent 提的、哪句是 agent 提了人改的——直接把「AI 写的东西怎么变成我的东西」这个焦虑，从道德问题降级成一个可查询的数据问题。这是我愿意为之付费的唯一理由，比产能理由更强。

**3. 我会把「拒绝」当成产出，而不是浪费。**

现在拒绝一个 AI 版本，那 10 秒是纯损耗。在 RefRain 里，一次带 reason 的 reject 是喂给下一轮的信号。这会让我更愿意用竞跑——因为落选的那两版不再是白烧的 token。

## 六、如果只能改一件事

**把「批量裁决」写进 SPEC，作为 Decision Batch 的一等语义。**

具体要求：跨 Proposal、跨 Review Slice 的多选，一次人类点击提交为一个 Decision Batch；提供「接受本 Proposal 全部 Slice」和「接受选中的 N 项」；reason 一律可空且无摩擦。

它不违反任何一条底线：Agent 依然没有写权限，合并依然由人类那一次点击触发，Decision Batch 依然原子、依然在冲突时整批拒绝、依然产生恰好一个 Text Head。变的只是**一次人类意志能覆盖多少个 slice**。

这一条不做，产品在场景 C 上每天向我收 30 分钟的税，我不会用到第二周；这一条做了，前面四条抱怨我都可以忍。
